How I build

Not a list of tools — the things I actually think about while I work.

Good UX

I think about how an interface feels before I worry about making it flashy.

Interaction, pacing, and clarity come first — visual polish is what I add once the experience already makes sense.

Accessibility

A beautiful interface isn't useful if people can't use it.

Keyboard navigation, screen readers, and color contrast aren't a pass at the end — I build with them from the start.

Readable code

I prefer simple solutions that another developer can understand months later.

Clever code is easy to admire and hard to maintain. I optimize for the person reading it next — often future me.

Learning by building

I learn technologies by actually making things with them.

I pick real, slightly-too-ambitious projects to learn a new tool, rather than working through it in the abstract.

About me

I'm a software engineer with a background in visual art, which shows up in how I approach engineering as much as how I approach design. Software engineering, UX, and visual design overlap more than people expect — all three are really about solving a problem for someone, clearly and with care.

Outside of client and product work, I make digital and 3D art, and I've been experimenting with Arduino and physical computing — mostly as a way to keep thinking with my hands.
