Overview

This is a full-stack web app for a clinic setting — a patient-facing experience for registering and booking appointments, and a separate staff dashboard for managing intake and scheduling. It's built for clinics that need registration and scheduling handled online rather than over the phone or on paper, and for the staff who have to keep track of who's coming in and why.

The problem

Patients and clinic staff both need a straightforward way to handle registration and appointment information — patients need to register and book without friction, and staff need a clear, centralized view of who's scheduled and what they've already shared with the clinic before they arrive.

I built this as a portfolio project rather than for a specific clinic, so this is based on general research into clinic intake workflows rather than direct interviews with clinic staff or patients.

The approach

Rather than building one shared interface for two very different audiences, I split the experience: a patient-facing registration and booking flow, and a separate staff dashboard, while keeping the underlying data model consistent between them. Because this handles patient information, I treated it as a HIPAA-informed project from the start rather than adding privacy considerations later. Design priorities:

  • Separate, purpose-built experiences for patients and staff
  • HIPAA-informed handling of patient data — audit logging, role-based access control, encryption-ready fields
  • A clear, multi-section intake form that doesn't overwhelm patients
  • A staff dashboard organized around the week's appointments, not a raw data table
  • A maintainable monorepo structure so frontend and backend stay in sync

Design & UX

The patient-facing flow is a multi-section intake form, broken into steps rather than one long form. The staff dashboard is organized around a weekly appointment view, so staff can see what's coming up instead of scrolling a flat list of every appointment ever booked.

Key features

Patient self-registration

Patients can register themselves online instead of over the phone or on paper.

Appointment scheduling

Patients can see available times and book an appointment directly.

Pre-visit symptom collection

Patients share relevant information before their visit, so staff have context going in.

Staff intake dashboard

A weekly view of upcoming appointments and patient-submitted intake information, in one place, for staff.

Technical implementation

The frontend is built with React (via Vite); the backend is a Node.js/Express API using Prisma as the ORM over a PostgreSQL database. The project is structured as a monorepo so the frontend and backend live and evolve together. Authentication uses JWTs with refresh tokens. Because the app handles patient data, it was built with HIPAA-informed principles from the start: audit logging, role-based access control, and encryption-ready fields in the schema — even though this is a portfolio project rather than a deployed clinical system.

Challenges & solutions

Challenge: designing for two very different users in one system

Patients and staff need very different things from the same underlying data — patients need a simple, guided flow; staff need a dense, at-a-glance operational view.

Solution

I split the frontend into a patient-facing flow and a separate staff dashboard, sharing the same backend and data model instead of duplicating logic.

Result

Each side of the app could be designed around what its actual user needed, without compromising either experience.

Challenge: the same PostgreSQL environment conflicts I'd hit on VITA

Multiple competing PostgreSQL installations on my machine caused version and connection issues here too.

Solution

Having already solved this on VITA, I recognized and resolved it much faster the second time around.

Result

A reliable local database connection, and confirmation that documenting a fix the first time actually pays off later.

Accessibility & responsive design

  • Semantic HTML across the patient form and staff dashboard
  • A multi-section form broken into manageable steps rather than one long page
  • Responsive layouts for both the patient- and staff-facing views
  • Full keyboard-navigation and screen-reader testing across both flows is still to be done
  • A color-contrast audit and reduced-motion support are planned but not yet verified for this project specifically

What I learned

Splitting the patient and staff experiences instead of forcing one shared interface made both sides simpler to design and build — it's a decision I'd default to earlier next time rather than trying to unify them first. Treating HIPAA-informed handling — audit logging, RBAC, encryption-ready fields — as a first-class requirement from the start, rather than an afterthought, also shaped the data model in ways that would have been harder to retrofit later. And running into the same PostgreSQL environment issue I'd already hit on VITA reinforced that documenting a fix the first time is worth the extra few minutes.

Future improvements

  • Usability testing with real patients and clinic staff
  • Deploy a live, demo-able version
